# Git Flow — Кофейня-пекарня

Этот файл описывает стандарты именования веток и коммитов, на которые ссылается
`AGENTS.md` («Шаг 1: … Используй описанные там стандарты для названия веток,
структуры коммитов и префиксов»). Если этот файл существует — агент обязан
следовать именно ему, а не своим дефолтным правилам.

## 0. Главное правило проекта

- Защищённые ветки: **`main`**. Прямые коммиты и `git merge` в `main` запрещены всегда,
  без исключений.
- На GitHub для `main` включено правило **«Require a pull request before merging»** —
  это значит, что прямой `git push origin main` физически отклонится сервером.
  Единственный путь изменений в `main` — через Pull Request.
- Также включено правило **«Require status checks to pass before merging»** —
  пока настроенные проверки (CI/GitHub Actions — линт, сборка, тесты) не завершатся
  успешно, кнопка Merge на GitHub недоступна, даже если PR одобрен. Это меняет
  поведение агента на Шаге 3 — см. п. 6.1.
- Любая задача (фича, багфикс, рефакторинг, доки) начинается с новой ветки от `main`.
- Порядок для агента:
  1. Работать в отдельной ветке (см. п. 1).
  2. По завершении — запушить ветку в origin (`git push -u origin <branch>`).
  3. **Не создавать Pull Request самостоятельно**, пока не получено моё явное
     разрешение: `Да, сливай`. Формулировки вроде «выглядит хорошо», «супер», «класс» —
     это НЕ разрешение.
  4. После разрешения — создать PR (`gh pr create`, если доступен GitHub CLI, иначе
     описать в отчёте прямую ссылку вида
     `https://github.com/<owner>/<repo>/compare/main...<branch>?expand=1`,
     чтобы я мог открыть PR вручную).
  5. Финальное нажатие «Merge pull request» на GitHub — за мной, если явно не сказано
     иное. Если разрешение прямо включает и сам merge (например: «Да, сливай, и смёржи
     сам через gh pr merge») — агент может смёржить PR через `gh pr merge`, но не раньше.
  6. Удаление ветки/worktree после merge — тоже только после подтверждения, что PR
     смёржен (или явного разрешения на удаление).
- Никаких force-push и `git push --force` в `main`; force-push в свою рабочую ветку
  допустим только при явной необходимости (например, `rebase` по моей просьбе).
- Пока разрешение не получено — ветка и открытый (если есть) PR остаются как есть,
  ничего не переоткрывать и не пересоздавать.

## 1. Именование веток

Формат: `<тип>/<краткое-описание-в-kebab-case>`

Опционально, если есть номер задачи/issue: `<тип>/<номер>-<краткое-описание>`

| Тип        | Когда использовать                                              | Пример |
|------------|-------------------------------------------------------------------|--------|
| `feature/` | новая функциональность                                            | `feature/cart-widget` |
| `fix/`     | исправление бага                                                  | `fix/cart-total-rounding` |
| `refactor/`| изменение структуры кода без изменения поведения                  | `refactor/prisma-client-singleton` |
| `chore/`   | рутина: зависимости, конфиги, CI, форматирование                  | `chore/update-tailwind` |
| `docs/`    | только документация (`.md`, комментарии)                          | `docs/architecture-update` |
| `test/`    | добавление/правка тестов без прод-кода                            | `test/orders-api` |
| `style/`   | чисто визуальные/вёрсточные правки без логики                     | `style/product-card-spacing` |

Правила именования:
- только латиница, нижний регистр, слова через дефис;
- без личных имён, дат и «мусорных» названий типа `fix2`, `test-branch`;
- название отражает суть задачи, а не файл («что делаем», а не «где»):
  `feature/admin-orders-status` лучше, чем `feature/orders-page-tsx`.

## 2. Структура коммитов

Используем **Conventional Commits**:

```
<тип>(<область>): <краткое описание в повелительном наклонении, с маленькой буквы, без точки>

[опциональное тело — что и почему, если изменение не тривиальное]

[опциональный футер — Breaking changes, ссылки на задачи]
```

### Типы коммитов (совпадают с типами веток)
`feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `style`, `perf`

### Область (scope) — по слоям проекта из architecture.md
`catalog`, `product`, `cart`, `orders`, `admin`, `auth`, `api`, `db` (Prisma/схема),
`ui` (общие компоненты), `telegram`, `storage` (Cloudinary), `deploy`, `seed`

### Примеры хороших коммитов
```
feat(cart): добавить zustand-store корзины с персистом в localStorage
fix(orders): исправить округление totalAmount при пустой корзине
refactor(db): вынести PrismaClient в singleton lib/prisma.ts
chore(deps): обновить next до 15.x
docs(architecture): описать разделение Server/Client компонентов
test(api): покрыть POST /api/orders валидными и невалидными payload
```

### Плохие коммиты (так не делаем)
```
fix                      # нет типа/области/описания
WIP                      # промежуточные "заглушки" не коммитим как есть
исправил баг             # нет типа и области, неинформативно
feat: added stuff         # неинформативное описание
```

## 3. Атомарные коммиты (savepoint'ы)

Согласно `AGENTS.md`, коммит делается автоматически при завершении логического блока,
не дожидаясь команды. Логический блок — это, например:
- добавлена и провалидирована Prisma-схема / миграция;
- реализован и протестирован вручную один API-роут;
- собран и работает один компонент (например, `CartWidget`);
- пройден `npm run build` / `npm run lint` без ошибок после рефакторинга.

Один коммит = одна логическая единица. Не смешивать в одном коммите, например,
правку схемы БД и правку стилей несвязанного компонента — это два коммита.

## 4. Изоляция параллельной работы (Git Worktrees)

Если задачи выполняются параллельно (несколько субагентов или фоновый процесс уже
занимает рабочую директорию) — согласно `AGENTS.md`, используется `git worktree`.

Соглашение по расположению и именованию worktree-папок:

```
../worktrees/<имя-ветки-с-заменой-слэша-на-дефис>
```

Пример:
```bash
git worktree add ../worktrees/feature-cart-widget -b feature/cart-widget
```

По завершении работы worktree удаляется командой `git worktree remove`
**только после разрешения на слияние** (см. п. 0).

## 5. Что делать при конфликтах

- Конфликты разрешаются в самой рабочей ветке (или в её worktree), не в `main`.
- Если конфликт неочевиден по смыслу (не просто форматирование, а расхождение
  в логике/данных) — агент останавливается и описывает мне суть конфликта,
  не выбирает сторону самостоятельно.
- После разрешения конфликта — отдельный коммит `chore: resolve merge conflicts in <файлы>`.

## 6. Финальный отчёт перед PR/слиянием

Ветка запушена в origin, но PR ещё не создан. Перед запросом на PR/слияние агент
обязан прислать (это уточнение к Шагу 3 из `AGENTS.md`, адаптированное под правило
«Require a pull request before merging»):
1. Название ветки и список коммитов в ней (`git log main..<branch> --oneline`).
2. Список изменённых/добавленных файлов.
3. Что именно реализовано/исправлено, в 2–4 пунктах простым языком.
4. Есть ли миграции Prisma, требующие `npx prisma migrate deploy` отдельно.
5. Известные ограничения/TODO, если есть.
6. Ссылку для создания PR (если PR ещё не открыт) или ссылку на уже открытый PR.
7. Прямой вопрос: создать ли PR / смёржить ли уже открытый PR — как описано
   в `AGENTS.md`, п. Шаг 3, но применительно к PR, а не к прямому `git merge`.

### 6.1 Required status checks

В репозитории включено «Require status checks to pass before merging» — PR физически
нельзя смёржить на GitHub, пока обязательные проверки (CI/Actions: lint, build, тесты
и т.д.) не позеленеют, даже если я уже сказал «Да, сливай».

Порядок действий агента:
- Если PR уже открыт — перед вопросом на слияние агент проверяет статус чеков
  (`gh pr checks <номер>`, если доступен GitHub CLI) и указывает его в отчёте:
  ✅ прошли / ❌ упали / 🟡 ещё выполняются.
- Если чеки ещё выполняются — не блокировать отчёт ожиданием: сообщить, что они
  в процессе, и что PR будет доступен к merge после их завершения.
- Если чеки упали:
  - агент анализирует лог упавшего чека;
  - если причина очевидна и связана с последними изменениями в этой ветке
    (тот же принцип, что и для упавшего `npm run dev` в Шаге 2 `AGENTS.md`) —
    самостоятельно чинит, коммитит фикс (`fix: … CI`), пушит и сообщает об этом
    в отчёте;
  - если чек падает повторно (2+ раза подряд) с той же ошибкой, или причина
    не очевидна — агент останавливается и описывает мне суть падения, не пытается
    бесконечно чинить вслепую (тот же принцип, что и для фонового процесса).
- Разрешение «Да, сливай», данное до того как чеки позеленели, не означает
  «игнорируй чеки» — агент дожидается их завершения и только потом либо мёржит
  сам (если это ему разрешено, см. п. 0), либо сообщает мне, что PR готов к merge.
- Никогда не обходить это правило локально (например, `git push --force` в `main`,
  прямые коммиты в защищённую ветку, отключение проверок) — обход правил защиты
  ветки запрещён в любом случае, даже "чтобы ускориться".

## 7. Прочее

- `.env.local` и любые файлы с секретами никогда не коммитятся ни в одну ветку.
- Если в процессе задачи потребовалось поправить `package.json`/lock-файл —
  это отдельный коммит `chore(deps): …`, не смешивается с фичей.
- Ветка, у которой после ревью запрошены правки, донакатывает новые коммиты
  поверх существующих (без `git commit --amend` и без `push --force`),
  чтобы история ревью была видна.
