# AGENTS.md — правила для ИИ-агентов в проекте "Кофейня-пекарня"

## 1. О проекте

Интернет-магазин кофейни-пекарни: каталог, страница товара, корзина, оформление заявки без
оплаты, админ-панель. Полное ТЗ —
[docs/about-project.md](docs/about-project.md).

## Стек и архитектура

Next.js 15 (App Router) + React 19 + TypeScript (strict), Prisma 5 + PostgreSQL, NextAuth 4,
Zustand 5 (только корзина), Tailwind CSS, Zod. Единое приложение без монорепо — фронтенд, API и админка живут в одном репозитории.

- Структура папок, роутинг, схема Prisma — [docs/architecture.md](docs/architecture.md)
- Почему выбран именно такой стек — [docs/technologies.md](docs/technologies.md)

## Оглавление правил

Правила разнесены по отдельным файлам в `.agents/rules/`. Файлы **не**
подключаются автоматически — перед началом задачи открой (`Read`) те из
них, что подходят по теме задачи, и следуй им. Если задача затрагивает
несколько тем сразу — открой все соответствующие файлы.

| Файл | Когда открывать |
| --- | --- |
| [.agents/rules/server.md](.agents/rules/server.md) | Задачи с запуском/сборкой сервера (`dev`/`build`/`start`), маршрутизацией App Router, серверными vs клиентскими компонентами, запросами к внешним API, env-переменными и секретами |
| [.agents/rules/code-style.md](.agents/rules/code-style.md) | Любая правка кода на TypeScript/React/Tailwind — перед написанием кода и перед тем, как считать задачу готовой (прогнать lint/tsc) |
| [.agents/rules/mcp.md](.agents/rules/mcp.md) | Использование MCP-инструментов: `chrome-devtools` (отладка в браузере, DOM/network/скриншоты) и `context7` (актуальная документация по React/библиотекам) |

Общее правило: если задача не попадает ни в одну из тем таблицы — можно
не открывать ни один из файлов правил.

## Ключевые технические правила

- **Server Component не ходит через `fetch()` на свой же `/api/*`** — читает Prisma напрямую
  через `lib/prisma.ts`. `/api/*` нужен только для мутаций из Client Component (корзина →
  заявка, формы админки) и точек с HTTP-границей (auth callbacks).
- **`"use client"` — на минимальном листовом компоненте.** Данные запрашиваются как можно выше
  по дереву (Server Component), интерактивность опускается вниз.
- **Zustand (`stores/cartStore.ts`) — только клиентское состояние корзины.** Каталог, заказы,
  сессия — серверные данные, в сторе не дублируются.
- **Секреты — только через `process.env` на сервере**, никогда с префиксом `NEXT_PUBLIC_`.
  Вызовы сторонних API (Telegram и т.п.) — из `lib/*`, обёрнуты в try/catch, не должны ронять
  основной флоу (создание заказа и т.д.).
- TypeScript strict, алиас `@/*` → `./*`.

## Дизайн-система

Все цвета, шрифты, отступы — только из токенов [DESIGN.md](DESIGN.md) (тёмная тема "moody
brasserie": Black Olive / Forest Ink / Lemon Zest / Warm Cream и т.д.). Не придумывать новые
значения на глаз. Скругления — почти нулевые (острый, unsoftened стиль) — не добавлять
`rounded-lg` и подобное без явной причины.


## Завершение задач и память проекта

Когда ты считаешь, что задача полностью выполнена, и код работает, ты ОБЯЗАН выполнить следующие шаги перед тем, как отчитаться мне:

1. Открой файл `/docs/progress.md`.
2. Запиши в него суть выполненной задачи в две-три строки, не больше. Пиши только какие файлы были изменены и что в них было сделано. И какие новые переменные окружения (.env) были добавлены (если были). Дату указывать не нужно, только номер задачи по порядку.
3. Если мы изменили структуру базы данных, актуализируй схему в `/docs/architecture.md`.
4. Воспользуйся навыком security-review из [.claude/skills/security-review/SKILL.md](.claude/skills/security-review/SKILL.md) для проверки на безопасность


#  Жизненный цикл задач и Git Workflow
Ты и любые твои субагенты ОБЯЗАНЫ строго следовать этому алгоритму при получении задачи на разработку новой фичи, рефакторинг или исправление бага.

## Шаг 1: Инициализация и выбор режима изоляции
- **НИКОГДА** не пиши код напрямую в защищенных ветках (`main`, `master`, `dev`).
- Перед началом работы вызови инструмент чтения файлов и проверь, существует ли файл `/docs/git-flow.md`.
  - **Если существует:** Прочитай его. Используй описанные там стандарты для названия веток, структуры коммитов и префиксов (feat, bug, chore и т.д.).
  - **Если не существует:** Используй стандартный подход (например, `feature/название-задачи` или `fix/описание-бага`).
- Перед внесением изменений определи режим своей работы:
  - **Сценарий А (Параллельная работа субагентов):** Если ты делегируешь задачи субагентам для параллельного выполнения или система уже выполняет другой процесс в этой директории, ты **ОБЯЗАН использовать Git Worktrees** Каждый параллельный процесс должен работать в своей изолированной папке на диске.
  - **Сценарий Б (Одиночный/Последовательный режим):** Если ты работаешь над задачей один и последовательно, используй стандартный флоу: просто создай ветку через `git checkout -b <branch-name>` в текущей директории.

## Шаг 2: Процесс разработки (Атомарные коммиты)
- Работай итеративно (строго внутри своей ветки или папки worktree).
- Как только ты успешно завершаешь крупный логический блок (настроил схему данных, дописал контроллер, тесты прошли успешно),ты **ОБЯЗАН автоматически создавать промежуточный коммит**.
- Не жди моей команды для этих коммитов. Это наша точка сохранения (savepoint) для безопасного отката.
- Пиши четкие сообщения коммитов по стандартам проекта.
- Мониторинг фонового процесса разработки: Если в рамках задачи запущен фоновый процесс (например, npm run dev, yarn dev и т.д.) и ты в процессе работы обнаруживаешь, что он упал или завершился с ошибкой (вылетело исключение, процесс остановился, порт освободился и т.д.):
    - НЕ жди моей команды и не продолжай работу молча.
    - Самостоятельно останови зависший/упавший процесс (если он всё ещё "висит" в терминале в нерабочем состоянии).
    - Проанализируй текст ошибки — если причина очевидна и связана с твоими последними изменениями (опечатка, неверный импорт и т.д.), сначала попробуй исправить причину.
    - После этого перезапусти процесс (npm run dev / аналог) заново.
    - Кратко зафиксируй в своём внутреннем логе/отчёте: что упало, в чём была причина (если удалось определить) и что был выполнен рестарт.
    - Если процесс падает повторно (2+ раза подряд) с той же ошибкой — остановись и сообщи мне, не пытайся бесконечно перезапускать вслепую.

## Шаг 3: Завершение и Ревью
- Когда ты выполнил все требования задачи и код работает, **ОСТАНОВИСЬ**.
- Сделай финальный коммит для своей ветки.
- Выведи мне краткий структурированный отчет: какие файлы изменены и какой функционал добавлен.
- В конце отчета задай прямой вопрос: 
  - *Если использовался Сценарий Б:* "Фича реализована. Проверяем работу, или я могу выполнить слияние (merge) с главной веткой?"
  - *Если использовался Сценарий А:* "Изолированная работа завершена. Могу ли я слить ветку в main и удалить временный worktree?"
- **СТРОГИЙ ЗАПРЕТ:** Никогда не выполняй `git merge`, не удаляй worktree и не создавай Pull Request без моего прямого текстового разрешения "Да, сливай".
